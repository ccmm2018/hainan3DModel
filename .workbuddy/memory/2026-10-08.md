## 修复 FloorPlan2D 编辑模式「拖动房间可换位置」无效

- 现象：编辑楼层(房间)模式下拖动房间没有任何效果（提示与实际不符）。
- 复现/定位：用 playwright-cli + 系统 Chrome 端到端测试（IndexedDB 种子楼层+房间数据）。
  - 楼层有真实入库房间时拖拽正常；
  - 楼层存在但无入库房间（显示 12 个演示房间 demo_0~demo_11）时拖拽完全无效。
- 根因：`roomBlocks` computed 中演示房间分支忽略 `gridPos`，永远按 `idxToSpan(idx)` 渲染，
  而 `applySpan` 只改 gridPos → 画面不动。
- 修复（均在 src/components/FloorPlan2D.vue）：
  1. roomBlocks 渲染统一 `gridPos[room.id] ?? idxToSpan(idx)`；
  2. 新增 `syncDemoGridPos()`：无真实房间时把演示房间也铺入 gridPos；有真实房间时清掉 demo_* 键（避免幽灵占格）；
  3. `rebuildGrid()` 末尾调用 syncDemoGridPos；
  4. `commitSpan()` 对 `demo_` 前缀房间直接跳过（合成数据不入库）；
  5. 编辑模式提示语按 `hasRealRooms` 动态：真实房间=原提示；演示预览=「仅本次浏览生效，导入图纸后编辑真实房间才会保存」。
- 验证：演示模式 movedDx 0→148；真实房间回归通过；vue-tsc 零错误；floorRoom.spec.ts 11 测试全过。

## 二次修复：拖拽换位需要拖过第二个房间 / 左右方向位置不准确

- 根因：旧移动算法用「光标所在格 − 按下时光标所在格」推位移，起始格由 Math.round(光标位置) 映射。
  抓取点偏离房间左上角时起始格会被算到邻格（抓正中 round(0.5)=1 直接落到邻格），
  导致换位阈值随抓取点漂移：有时要拖过整整一个房间、有时一碰就跳、左右不对称。
- 修复（FloorPlan2D.vue onRoomDown + onStageMouseMove move 分支）：
  1. 改为「抓取偏移跟随」：按下时记录光标相对房间矩形左上角的世界坐标偏移 dragGrab，
     拖拽中目标左上角 = 光标 − dragGrab，再 Math.round 吸附到最近格 → 抓哪里阈值都一致（0.5 格）、左右对称；
  2. 换位仅在目标格变化时执行；快速甩动一次跨 2 格压到 2 个房间时整步回退（含被换房间），保证网格任何时刻不重叠；
  3. 删除无引用的 floorToCell / dragStartCell / dragStartFloor；move 分支用局部 rid 修 TS2538（回调内 ref 收窄丢失）。
- E2E 实测（6 房间网格，抓取点 0.1/0.5/0.9 归一化位置）：拖 0.6 格均恰好移动 1 格并与邻房互换、
  反向拖 0.6 格精确复位、快速甩 2.6 格后各占一格无重叠。vue-tsc 零错误。

## 三次修复：互换后整层跳动 / 未分配房间互换"没反应"或搬运其它房间

- 根因 1（整层跳动）：`fit` 与 `projectionCenter` 都把房间轮廓纳入计算，松手 commitSpan 写回新轮廓
  → 视图变换重算 → 整层缩放/平移跳一下，gridGeom 随 fit 变化导致互换房间位置二次偏移。
  修复：有外轮廓时 fit/projectionCenter 只用楼层外轮廓（fit 额外纳入外轮廓 z=0 楼板底面防裁切），
  无外轮廓（演示态）才兜底用房间。
- 根因 2（没反应/搬运其它房间）：旧交互"拖动途中每跨一格就和沿途房间交换"——外观相同的房间互换
  看似没反应，继续拖又把下一间换走。修复：拖动途中只移动被拖房间（允许暂时视觉压叠，
  dragTopBlocks 把被拖房间置顶绘制），交换统一留到松手时按落点格做一次：
  落点被 1 间占据→互换（对方搬回被拖房间原位，按自身尺寸锚定夹紧，压到第三方则回弹原位）；
  落点空→直接落位；同时压到 ≥2 间→无效落点回弹原位。commitSpan 同时持久化被换房间。
- 删除不再使用的 applySpan。
- E2E 实测：拖动途中其它房间像素位置与拖前完全一致；松手互换后两房精确对调、其余房间像素分毫不动
  （证明视图变换零跳动）；反向互换精确复位。vue-tsc 零错误。
- 测试环境备忘：playwright-cli 的 browser session 在两次 Bash 调用之间会被回收 → 必须把 open+操作+断言串在同一条 bash 命令里；snapshot --filename 输出在项目根目录而非 .playwright-cli/。

## 优化：低配机器「模型加载 100% 后卡近 30 秒」

- 用户反馈低配电脑上进度到 100% 后还要等近 30 秒模型才出现。100% 后的主线程重活：
  GLB 同步解析（含贴图解码）→ 4 段贴图后处理（每段本身是整块同步循环）→ 首帧 GPU 上传。
- 修复（MapScene.ts + SceneView.vue）：
  1. 新增 `onModelStage(label, done, total)` 回调，遮罩显示当前阶段（解析模型数据…/解码贴图/优化贴图/检测损坏贴图/准备渲染）；
  2. `runChunked()`：每段拆成 ~14ms 小片、片间 rAF 让出帧并汇报进度；
  3. `predecodeTextures()`：HTMLImageElement 路径并行 img.decode()（原来首次 drawImage 才逐张串行懒解码）；
  4. lowEnd 顺序调整：先缩贴图（reduceTextureForLowEnd）再黑图检测，尽早把 450MB 大位图换成 ≤512 canvas 降内存峰值；
  5. 四段后处理重构为单张函数（clampTextureToMaxSize/makeTextureWebGL1Safe/fixMatMapIfBlack/reduceTextureForLowEnd）+ collectTextures/collectMatMapPairs 收集器 + facadeCache/blackSampleCtx 字段复用；
  6. 每段输出耗时日志（`[MapScene] xxx：n 项，耗时 xms`），后续慢加载可精确定位热点段。
- 验证：vue-tsc 零错误；E2E 分片日志正常（缩放超大贴图 77 项 0ms / 检测损坏贴图 57 项 4ms）、遮罩正常揭开、模型渲染、取景收敛。
- 备注：若低配上仍慢且日志显示大头在「下载+解析」或首帧上传，下一步方向是 GLB 资产瘦身（Draco/meshopt/贴图压缩）或 IndexedDB 缓存处理后的贴图。

## 优化：低配机器空闲 CPU 90%+ / 操作后卡顿

- 根因：AMap GLCustomLayer 每帧清空本层画布并回调 render()，旧实现每帧都做整场景 three.js 重绘
  （几百个 draw call），空闲时也如此 → 低配 CPU 持续 90%+；高亮每次 mousemove 换楼都克隆整套材质。
- 修复（MapScene.ts）：
  1. 低配帧缓存合成 `renderWithFrameCache()`：整场景画进 WebGLRenderTarget，
     视角/内容未变的帧只做一次全屏贴图（1 draw call）。markDirty/requestRender/视角签名变化时置脏
     `frameCacheDirty` 重绘一次。RT 线性存储（不设 colorSpace），blit 用 MeshBasicMaterial
     (toneMapped=false, transparent) 补 sRGB 编码，与直绘路径像素一致。
  2. 冻结模型子树矩阵 `freezeModelMatrices()`（modelRoot 自身保留自动更新，校准不受影响）；
  3. 高亮材质缓存 `highlightMatCache`（key: 颜色|原材质uuid），clearHighlight 不再 dispose；
  4. enterIndoorView/exitIndoorView/setMapView 补 markDirty；
  5. `?lowend=1/0` URL 参数强制低配开关（测试/排查用）；destroy 释放 RT/blit/材质缓存。
- 验证：vue-tsc 零错误；159 个测试全过；?lowend=1 截图与模型/底图合成正常（无黑边/光晕/双预乘）；
  两模式点击建筑弹窗均正常（拾取+高亮+缓存失效链路 OK）；空闲 3 秒长任务 0 个。
