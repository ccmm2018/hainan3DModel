## 低配机器拖拽/缩放 CPU 仍高（80%）+ 页面加载瞬间峰值
- 排查结论：模型本身极轻（GLB 90 mesh、~4000 三角形、116 贴图、1.09MB），每帧三维渲染几乎不占 CPU。
  拖拽/缩放 80% 与加载瞬间峰值的主因是**高德底图自身全屏实时渲染**，尤其是 `mapFeatures` 里的 `building`（周边 3D 楼块），
  它随地图平移/缩放逐帧重新拉伸渲染，是弱机最大开销。
- 修复 1（主）：`src/config/mapConfig.ts` 的 `mapFeatures` 由 `['bg','road','building']` 改为 `['bg','road']`，
  关闭周边 3D 楼块（保留地面轮廓+路网）。校园数字孪生以自有 3D 模型为核心，周边 3D 楼块既冗余又昂贵。需要立体感可加回 'building'。
- 修复 2（节流）：`src/core/MapScene.ts` 的 `render()` 增加相机同步节流——视角签名未变时跳过 `getCameraParams()` 重算与 `updateProjectionMatrix()`，
  复用上一帧相机；拖拽/缩放视角每帧变化仍逐帧同步（保证模型跟手），仅削减静态/空闲帧的无效开销。
- 验证：vue-tsc 0 错、vitest 152/152 通过、`vite build` 成功。
- 备注：低配判定 `lowEnd = hardwareConcurrency<=4 || deviceMemory<=4`；低配已关阴影/关 PMREM/像素比封顶 1。
  若加回 'building' 后拖拽 CPU 回升，可进一步考虑低配时把 MeshStandardMaterial 降级为 MeshLambert（降低每帧片元开销），但会带来观感变化、需用户确认。

## 2.5D 图层三处bug「改了没生效」的真正根因（重要修正）
- **上一轮误诊**：以为主因是 `roomFills` 用常量 `NORMAL_TOP` 且遍历 `displayedRooms`。其实用户看到的房间色块来自 `roomBlocks`（合成网格，行 ~807+），上一轮只改了 `roomFills`（仅 renderStage≥5 的 3D 盒子副路径），所以"颜色/隐藏"完全没变化。
- **真正根因（两条路径都有）**：
  1. `roomBlocks` 给普通房间写死常量 `NORMAL_TOP`、遍历 `displayedRooms`（含隐藏房间）→ 颜色不随状态变、隐藏只变暗不移除。
  2. **demo/合成预览路径**：当该楼无导入 DXF 时 `displayedRooms` 回退到合成 `demos`；而 `saveEdit` 因 `currentFloor` 为 null 直接 return（名称根本没存）、`hideRoom`/`setUseStatus` 写入 `synthOverrides` 但**渲染从未读取它** → 名称/状态色/隐藏三条全失效。
- **修复（src/components/FloorPlan2D.vue）**：
  1. 新增 `effectiveRoom(room)`：把 `synthOverrides[id]` 合并回房间；`liveRoom` 与 `roomBlocks` 的 source 都先过 `effectiveRoom`。
  2. `roomBlocks.source`：真实房间用 `visibleRooms`（过滤隐藏）；合成房间 `demos.map(effectiveRoom).filter(selected!==false)`。`topFill = colorFor(room)`（状态/着色模式驱动），`textColor` 按 `isLight(fill)` 自动深/白字。
  3. `saveEdit`：真实房间写 store；合成房间改写入 `synthOverrides`（不再因 currentFloor 为 null 直接 return）。
- 验证：vue-tsc 0 错、vitest 152/152、vite build 成功。
- **关键经验**：FloorPlan2D 的真实房间渲染主路径是 `roomBlocks`（平铺色块网格），`roomFills` 只是高配 3D 盒子；改房间颜色/隐藏必须动 `roomBlocks`。合成预览数据经 `synthOverrides` 中转，渲染侧必须读取它。
